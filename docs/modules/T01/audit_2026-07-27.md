# 4. EvidenceCard Generation Audit



## 4.1 RAG Evidence Generation

Location:

```

app/rag/[evidence.py](http://evidence.py)

```

Observed behavior:

EvidenceCard generation uses fallback logic:

```

abstract

   ↓

summary

   ↓

title

```

to construct:

```

quoted_text

```

Finding:

When higher-quality text evidence is unavailable,

metadata-level fields may become quoted_text fallback.

Potential risk:

A title or metadata field may be interpreted downstream as evidence content.

Required future improvement:

EvidenceCard should distinguish:

- verified source quotation;
- metadata information;
- insufficient evidence.

# 12. Evidence Catalog Boundary Audit



## Target

The baseline audit additionally inspected the evidence catalog generation boundary.

The inspected path is:

app/workflow/[pipeline.py](http://pipeline.py)  
|  
v  
_evidence_catalog  
|  
v  
EvidenceCard generation  
|  
v  
downstream evidence references

```


The purpose of this audit is to verify whether evidence provenance is preserved before evidence objects are used by downstream scientific reasoning components.



## Findings


The current pipeline contains an evidence catalog stage responsible for organizing evidence objects before downstream usage.


Observed properties:


- Evidence objects can be propagated through the workflow.
- Evidence identifiers can be carried into downstream references.
- Evidence generation and reference paths are already present in the current architecture.


However, the baseline audit identified several contract-level gaps at the evidence catalog boundary:


### 1. Quote preservation


The current evidence catalog boundary does not enforce that every evidence object contains the original quoted text.


Risk:

Evidence objects without preserved source text may lose traceability during downstream reasoning.



### 2. Locator completeness


The current catalog path does not require complete source location information for every evidence object.


Risk:

Evidence references may become difficult to reproduce or manually verify.



### 3. Provenance validation


The current workflow does not enforce source type and verification status before evidence objects enter downstream claim generation.


Risk:

Incomplete or insufficiently verified evidence may be incorrectly treated as established scientific support.



## Impact


The audit indicates that evidence identity propagation exists, but evidence quality constraints are not fully enforced at the catalog boundary.


To address these issues, this PR introduces an evidence contract layer containing:


- evidence_id
- source_type
- quoted_text
- locator
- verification_status


The contract layer defines the required evidence structure without replacing the existing runtime EvidenceCard implementation.


Future runtime integration should validate evidence objects at the catalog boundary before they enter scientific reasoning workflows.
```
